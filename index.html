01 — The stack

A compiler, a kernel, and a transaction.

Most robotics stacks decide between processes you can isolate and code you can run quickly. Shinro does not make that trade: the artifact is small and self-contained, and the system that runs it keeps every module accountable.

01 · COMPILE

Shinro compiler

Traces a trained policy, lowers it to a typed dataflow graph, and emits a kernel as one shared object. Memory is sized at compile time and constants are folded into the graph — no interpreter, no Python, no ONNX Runtime.

policy.onnx → one .so kernel
02 · SUPERVISE

Cake resident

An in-process supervisory control plane. Modules are capsules — content-addressed and signed — bound through declared, versioned contracts that are resolved into a hashed Plan before the first tick.

capsule → contract → hashed plan
03 · REPLACE

Swap as a transaction

replace-slot computes the dependent closure, drains the retiring generation, rebinds under an epoch guard, publishes the new binding, and reclaims the old — as one supervised update.

closure → drain → rebind → activate

02 — Where it sits

Three ways to run the same policy.

The difference is not raw speed. It is what happens when one of the parts has to change while the machine is moving.

✓ built in ~ possible, but not as a supervised transaction ✕ not out of the box

Property ROS 2 / DDS Bare dlopen Cake
Fault containment (separate address spaces) ✓Yes ✕No ✕No
No serialization on the 50 Hz path ✕No ✓Yes ✓Yes
Replace a running module without a restart ~Partial ✕No ✓Yes
Signed artifact, contracts checked before it runs ~Partial ✕No ✓Yes
Session identity survives the swap ✕No ✕No ✓Yes
What you deploy daemons + DDS one .so one .so + a small resident

The ROS 2 column assumes the default DDS RMW. rmw_zenoh replaces discovery and can share memory, but rcl still serializes the message before the RMW sees it — and the lifecycle picture does not change.

ROS 2 / DDS

Real isolation and a driver ecosystem, paid for on the hot path: serialization, discovery, jitter. Replacing a module at runtime means a process restart or a lifecycle dance — the swap is the risky part.

Bare dlopen

The fastest thing you can ship, and the shortest path to a segfault. No contracts, no admission, no drain: reloading a .so under a 50 Hz loop is a bet on your own bookkeeping.

Cake

Keeps the dlopen artifact and adds the transaction: signed capsules, versioned contracts, a drain, a rebind under an epoch guard, and a session that never restarts. One process, by design: the isolation is at the interface, not the MMU — a bad write inside a capsule can still take the session down. The kernel contains the swap, not the fault.

03 — Evidence

Same robot, same brain. Two stacks.

We ran Pollen Robotics' walking policy two ways: their runtime the way they intend it, and Cake the way we intend it. Same bytes, same 50 Hz loop, same simulated duck. Only one of them can replace parts of itself mid-stride.

Pollen gives you a robot. Cake gives you a robot whose parts are supervised.

Microduck reference demo · MuJoCo, 50 Hz
UNCHANGED

Session identity

Across every swap the resident's session identity stays bit-for-bit identical. No re-run of main(), no re-initialised device sockets.

MEASURED

Zero missed ticks

The loop holds 50.0 of 50.0 Hz through the replacement — during the trajectory swap and during the policy swap.

HONEST

What it can't do

A runtime swap guarantees memory and execution continuity, not physical state continuity. Gait-to-gait transfer is a control problem, not a kernel one.

Reproduce it in two minutes.

No physical Microduck required — the demo is a complete, self-contained MuJoCo simulation. The Cake release is pinned, checksummed and signed, and the fetcher verifies both.

quickstart.sh
$ git clone https://github.com/Shinro-xyz/shinro-demo-microduck.git
$ cd shinro-demo-microduck
$ make venv && make install PYTHON=.venv/bin/python
$ make fetch-cake PYTHON=.venv/bin/python
$ make cake PYTHON=.venv/bin/python # circle → eight → slalom
