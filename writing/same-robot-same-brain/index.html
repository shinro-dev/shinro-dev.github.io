01A robot should be able to change its own parts while it's walking

Microduck is a 25 cm, 14-servo biped (15 if you include the beak actuator). Its walking policy is a PPO-trained neural network by the Pollen Robotics team and obtained from Hugging Face.

That was deliberate. Keeping the neural networks the same allowed us to answer the only question that matters to anyone shipping robots on the field: what does the deployment stack around the robot look like?

So we ran both, faithfully: Pollen's runtime the way Pollen intends it, ours the way we intend it. Same robot. Same policy. Two very different machines.

02The fork every robotics team hits

Deploy a control policy onto real hardware and you land on one of two unhappy roads:

  • The heavyweight middleware path. Split your components across processes (ROS 2 / DDS). You get isolation between processes, but it comes at the cost of serialization, runtime discovery, and network jitter, plus a multi-gigabyte footprint. On a robot as small as the Microduck, that is a death sentence for anything that has to stay upright through tick-precise updates.
  • The bare dlopen path. Cram everything into one process. It is fast and deterministic, but swapping binaries is a tightrope walk over an impending segfault: there are no interface contracts and no lifecycle guarantees.

Both roads accept the same lie: that a robot's parts are too dangerous to change while the robot is running. It does not have to be this way. Cake is a supervisory control plane that runs in-process and treats a running robot's parts as modular components you can replace atomically, under supervision, and without dropping a tick.

03We ran Pollen's stack the way Pollen intends it

Credit where it's due: Pollen's stack works, and it's serious engineering. scripts/duck-sim starts the real robotd, the same binary a duck on a shelf runs, with the servo bus swapped for duck_control::sim::RemoteIo, driving a duck in MuJoCo. The policies are their official ONNX set, loaded into named slots (walk, stand, sitstand, ground_pick, kick_left, kick_right, roulade), and robotctl is how you talk to it. It's a complete runtime featuring IPC, BLE, odometry, config, updater, and media.

We ran it. It stood up, walked on command, and held its loop:

loop 50.0 of 50.0 Hz · 0 missed

And it can swap a policy live: robotctl policy load walk <file> rebinds a slot with robotd never restarting. That's real. That's the bar we were up against.

Now here's what Cake changes.

04Cake vs Pollen, side by side

Same robot. Same policy. Each run the way its authors intended.

Property Pollen · duck-sim Cake · make cake
what it is a full robot runtime (robotd + daemons) an in-process supervisory kernel
the policy the official alpha_walking.onnx the same bytes, compiled to one .so
what runs the network ort → libonnxruntime.so the compiled VM — no onnxruntime
what you install the daemon stack + libonnxruntime.so one 790 KiB .so, zero runtime deps
how modules talk robotd's own IPC zero-copy tables + declared contracts + epoch guards
the 50 Hz loop 50.0 / 50.0 Hz, 0 missed 50 Hz, held through the swap

what you can replace a policy slot (7 of them), live any binding — a trajectory provider, or the policy leaf

the runtime you avoid onnxruntime — a 21 MB shared library, ~130 MB installed nothing; the artifact is the policy

What Cake gives you that a file swap can't:

  • A policy that ships as one artifact. The same network, compiled by the Shinro compiler to a single 790 KiB .so binary with no onnxruntime, no numpy, no Python in the process. The binary has deterministic memory allocated at compile time, which prevents the footprint creep commonly seen with onnxruntime on edge devices.
  • Replacement that is a transaction. replace-slot computes the dependency closure, drains the retiring generation, rebinds under an atomic epoch guard, publishes the new binding snapshot, and reclaims the old, as one supervised update, with cryptographic capsule admission and versioned contracts checked before it runs.
  • Any binding is swappable, not just a policy slot. In a file-swapping runtime, dynamic reloading is bespoke: the daemon must write dedicated plumbing for each specific asset type it anticipates reloading. Pollen's stack has no counterpart for hot-swapping a trajectory provider, because the command is an internal intent (pad / scheduler / deadman), not a hot-reloadable slot. Cake doesn't care what a module computes; whether it's a trajectory generator, an estimator, or a policy leaf, as long as it matches its versioned descriptor, replace-slot hot-swaps it using the exact same kernel transaction.

Pollen's offline policy-rehearsal reports ~14 ms for a single session.run, while a plain onnxruntime run of the same model in the same process is ~17 µs, so that's their harness/config, not the network, and we're not going to print it as a win. The real headline isn't the forward pass anyway. It's the layer around it: a dependency-free artifact, a transactional replacement instead of a file swap, and a robot whose parts are supervised.

05The demo: swapping a robot's trajectory mid-stride

On the Cake plane, Microduck decomposes into supervised modules:

  • The policy module runs the compiled inference VM: 61-D observation in, 14-D joint offsets out, at 50 Hz (a hard 20 ms tick budget).
  • The trajectory module reads the trunk pose, runs closed-loop pure pursuit, publishes a 13-D command block.

The trajectory module is pure dataflow. As the robot walks, we trigger live module updates through Cake's administration probe:

  • 0–8 s — the robot follows a circle.
  • 8 s — Cake runs replace-slot → figure-8.
  • 16 s — Cake runs replace-slot → slalom.

What happened to the robot?

Nothing. It never stumbled, never restarted, never dropped a tick. The transaction completed, the session identity stayed bit-for-bit identical, and the walk continued as the robot adjusted to its new target trajectories.

Reproduce the whole sequence yourself: the walk, both swaps, and the log, with the Microduck demo on GitHub.

06Under the hood: what replace-slot actually does

In traditional systems, swapping a live component means pausing the world, resetting buffers, or praying your mutexes don't invert priorities. Cake treats a module upgrade as an atomic transactional closure:

  1. 01 Compute closure who reads this slot?
  2. 02 Drain prepare_quiesce hook
  3. 03 Rebind live_snapshot under epoch guard
  4. 04 Publish & activate new binding snapshot
  5. 05 Reclaim retired generation's memory

The guarantees doing the work here:

  • Admission before execution. Capsules are content-addressed and cryptographically signed. An unverified or ABI-mismatched blob cannot enter a running resident.
  • Declared, versioned interfaces. Descriptors declare exact contracts with semantic versioning, resolved statically in a hashed Plan before a single tick runs.
  • The epoch guard. The policy reads its command inputs under an epoch guard, so it always sees a consistent slice: no torn reads, no half-written vectors, no locking overhead.
  • Unbroken session identity. Across every swap, the resident's session identity is identical. It never re-runs main(), never re-initializes device sockets, and never leaves unmonitored dead time.

One thing that list does not include: fault containment. Everything above runs in one address space, so a bad write inside a capsule can take the session with it, and there is no sandbox for untrusted capsules. What the kernel guarantees is the transaction, not the fault.

07The harder half: swapping the policy itself

The trajectory module is pure dataflow, which is what makes it a clean thing to replace. The policy is harder, because in the obvious design the policy is the thing that owns the loop. A module that owns the clock cannot be replaced without taking the clock with it: replace-slot drains the retiring generation, the thread that owns the sim socket goes down, and the plant link goes with it.

We ran that first. The fused policy module owns the socket and the 50 Hz tick; swapping it returns COMPLETED, the session identity is unchanged, and the walk ends, the sim client sees the connection go away and stops, about two seconds into a six-second run. The transaction is atomic, but atomic is not the same as bumpless. The swap completed and the robot stopped walking.

The fix is a topology change, not a special case in the kernel. Move the socket and the clock into a stable bridge module that is never swapped, and make the policy a leaf the bridge consumes with a live binding. Through the swap the bridge keeps ticking, re-reads the policy's action table from the epoch-guarded binding snapshot, and when the table address changes, meaning a new policy generation has been committed, cross-fades from the outgoing network's action to the incoming one over 25 ticks. The blend happens in the one place that sees both generations at once, so the hand-over is bumpless.

Fused versus split: the same transaction, the same session, and only one of them still walking.

  • Fused policy swap. The transaction reads COMPLETED and the session identity is unchanged, but the plant link is torn down. The sim client exits and the duck stops at the swap.
  • Split policy swap (make policy-swap). The same transaction, the same unchanged session, but the stable bridge holds the plant link. The duck stands, then walks.

Run it: make policy-swap. The duck balances in place under the standing network for the first two seconds, Cake points the policy slot at the walking capsule with the same replace-slot it used for the trajectory, and then it walks the circle. The transaction reads COMPLETED, the session identity is bit-for-bit unchanged, and the bridge held the plant link for the whole window: steps=511, travel=1.155 m, speed=0.113 m/s.

One honest caveat on bumpless transfer. The swap from stand → walk succeeds because the standing policy holds the duck near zero velocity while the walking network phases in. The reverse, walk → stand, completes the software transaction and holds the link just as cleanly, but the duck falls (tilt ≈ 175°). A runtime swap guarantees memory and execution continuity, but it cannot invent physical state continuity: the standing network expects a static base and is not an active mid-gait recovery controller. Linearly cross-fading raw joint actions across 25 ticks bridges the software lifecycle, but true bidirectional transfer across disparate gaits ultimately requires dynamic phase matching or an intermediate deceleration manifold, which is a control theory and locomotion problem rather than a kernel problem.

And because the split's bridge and leaf each own a 50 Hz thread, they are loosely coupled: the heavy render profile can starve one of them and the duck can fall before the swap, which is why the demo defaults to the lighter one. Scheduler lockstep would remove that sensitivity.

It ships as its own release. The policy-swap bundle carries the split, the stable bridge, the standing and walking policy leaves, and the trajectories, and no fused capsule; it is versioned separately from the trajectory demo so the two can be released independently.

08Try it on your machine (in two minutes)

No physical Microduck required — it is a complete, self-contained MuJoCo simulation:

shell · zsh
# 1. Clone the demo repo
git clone https://github.com/Shinro-xyz/shinro-demo-microduck.git
cd shinro-demo-microduck

# 2. Set up and pull the verified Cake release
make venv
make install PYTHON=.venv/bin/python
make fetch-cake PYTHON=.venv/bin/python

# 3. Run the live-swap walk (circle → eight → slalom)
make cake PYTHON=.venv/bin/python

A successful run takes about 24 seconds: the duck walks the circle for eight seconds, takes the figure-eight at 8 s and the slalom at 16 s, and does not stop. Both transactions read COMPLETED against the same session id.

You get the full telemetry:

  • state/media/microduck_cake_walk.gif — the rendered walk, colour-coded by trajectory.
  • state/media/microduck_cake_swap.png — the transaction phase diagram.
  • state/run/swaps.json — proof that each transaction hit COMPLETED while the session identity stayed unchanged.

Want the one that turns heads? The policy swap is its own release: make fetch-cake-policy-swap then make policy-swap swaps the policy itself: a standing network for a walking one, live, without the walk stopping.

09The takeaway

Modern robotics doesn't need heavier frameworks. It needs better systems guarantees.

Cake takes the one policy everyone already has and gives it what a shipped product actually needs: a single dependency-free artifact, cryptographic admission, verified interface contracts, and atomic in-process lifecycle management, with the lifecycle guarantees of a microkernel and the speed of raw memory.

Pollen gives you a robot. Cake gives you a robot whose parts are supervised.
